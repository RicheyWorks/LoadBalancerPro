# API Security And Abuse-Resistance Posture

LoadBalancerPro's HTTP API is intended for controlled lab validation, CI validation, and controlled operator review. The application includes app-level guardrails, but it is not a complete internet-edge security boundary by itself.

For copyable run commands that exercise local demo, prod API-key, cloud-sandbox API-key, OAuth2, and proxy-loopback boundaries, start with [`OPERATOR_RUN_PROFILES.md`](OPERATOR_RUN_PROFILES.md).

For the cockpit auth and Swagger/OpenAPI gating roadmap/current phase notes, see [`ENTERPRISE_COCKPIT_AUTH_PLAN.md`](ENTERPRISE_COCKPIT_AUTH_PLAN.md).

For placeholder-only Postman review of local/demo and prod API-key boundaries, use [`POSTMAN_COLLECTION.md`](POSTMAN_COLLECTION.md). It documents the enterprise lab collection, local environment, local-only safe smoke harness, Swagger/OpenAPI gating checks, sanitized evidence export, and the no-real-secrets rule.

## Authentication Posture

The unqualified default profile selects API-key mode and refuses startup when `loadbalancerpro.api.key` is missing or blank. The explicit `local` and checked-in proxy-demo profiles select `loadbalancerpro.auth.mode=none`, emit a prominent authentication-disabled warning, and must remain bounded to loopback development or tests. Production-like deployments should use a configured API-key mode or OAuth2 mode; a profile name does not weaken API-key enforcement.

The checked-in Dockerfile defaults `SPRING_PROFILES_ACTIVE=prod`, so container/default deployment mode is protected by the prod API-key profile. Provide `LOADBALANCERPRO_API_KEY` through the operator's runtime secret/config system for protected prod container usage; do not bake API keys or OAuth2 tokens into the image.

API-key mode protects `/api/**` with `X-API-Key` regardless of active profile, including read-only onboarding routes and the non-executing `POST /api/proxy/private-network-live-validation` command contract. The explicit public API exceptions are `GET /api/health` and unauthenticated `OPTIONS`; Actuator health/info exposure is configured separately. The same API-key boundary protects `/proxy/**`, `/v3/api-docs`, `/v3/api-docs/**`, `/swagger-ui.html`, and `/swagger-ui/**`. A missing or blank configured key prevents application startup, while a missing or wrong request header returns HTTP 401 after a valid key has allowed startup. API-key mode is a compatibility gate, not a full identity or role model. OAuth2 mode provides bearer-token validation and explicit route roles when issuer or JWK settings are supplied. The current matrix assigns operator access to allocation, routing mutations, proxy, Enterprise Lab, evidence-training, remediation, and scenario-replay prefixes; read roles to LASE shadow, lab scenario reads, and routing scenario reads; and the separate admin role to durable retention and compaction. Unclassified `/api/**` routes are denied. OAuth2 application roles are mapped only from dedicated `roles`, `role`, `authorities`, and `realm_access.roles` claims. Standard OAuth2 `scope` and `scp` claims are not promoted to `ROLE_*`; enterprise IdPs should emit the configured `observer`, `operator`, and `admin` app roles in dedicated role claims. Missing or ambiguous role claims fail closed for role-required routes. See [`IDP_CLAIM_MAPPING_EXAMPLES.md`](IDP_CLAIM_MAPPING_EXAMPLES.md) for operator/admin examples and [`ENTERPRISE_AUTH_PROOF_LANE.md`](ENTERPRISE_AUTH_PROOF_LANE.md) for mocked IdP/JWKS proof, scope-only denial evidence, token lifetime guidance, and key-rotation examples that use no real IdP secrets.

Deployments that expose the service beyond a private test network should place it behind a trusted ingress, API gateway, reverse proxy, or zero-trust access layer.

Proxy concurrency limits, adaptive limiting, and priority-aware load shedding are process-local overload controls, not authentication, authorization, a distributed quota, or a cross-replica global cap. Priority mapping is disabled unless `loadbalancerpro.proxy.shedding.priority-header` is configured. If enabled, the deployment must remove caller-supplied copies and set the header at a trusted authenticated ingress; allowing untrusted callers to claim `CRITICAL` priority defeats priority ordering, although the strict concurrency cap still applies. Keep edge admission controls in place for shared or public deployments.

## CSRF Disposition

LoadBalancerPro keeps protected API/proxy paths stateless. Spring Security is configured with stateless sessions, form login disabled, HTTP Basic disabled, and logout disabled. API clients authenticate with explicit request headers in protected modes: `X-API-Key` for API-key mode or `Authorization: Bearer ...` for OAuth2 mode.

CSRF token enforcement is not required for those stateless header-auth API/proxy calls because they do not rely on browser ambient cookie credentials. The security configuration therefore scopes CSRF token checks away from `/api/**`, `/proxy`, `/proxy/**`, and Actuator paths while preserving the existing API-key/OAuth2 boundaries. If future work introduces session-cookie authentication, form login, browser ambient credentials, or credentialed cross-site browser flows for protected mutation endpoints, this CSRF disposition must be re-evaluated before that change ships.

## Rate-Limit Posture

The application uses validation, request-size limits, structured errors, cloud-safety boundaries, and an optional process-local API rate limiter as app-level protections. The optional limiter is disabled by default with `loadbalancerpro.api.rate-limit.enabled=false` so local/demo workflows stay convenient. When enabled, it applies a token bucket to allocation, routing, scenario replay, remediation, Enterprise Lab `/api/lab/**`, proxy control/status, LASE shadow observability, and `/proxy/**` surfaces while leaving `GET /api/health` and unauthenticated `OPTIONS` preflight outside the bucket.

Configure the optional process-local limiter with `loadbalancerpro.api.rate-limit.capacity`, `loadbalancerpro.api.rate-limit.refill-tokens`, and `loadbalancerpro.api.rate-limit.refill-period`. `loadbalancerpro.api.rate-limit.trust-forwarded-for` defaults to `false`; enable it only behind a trusted ingress that sanitizes `X-Forwarded-For`. The limiter returns structured `429 rate_limited` JSON plus a `Retry-After` header and must not log or persist API keys, bearer tokens, request bodies, or credentials.

This is not a distributed quota system and does not depend on Redis, a database, or an external queue for throttling. Apply rate limiting at the edge for shared or public deployments. A reasonable first edge policy is to limit POST requests to allocation, evaluation, and routing endpoints per client identity or source IP, with stricter limits for repeated `400`, `401`, `413`, `415`, and `429` outcomes.

## Abuse-Resistance Guarantees

The API rejects malformed JSON, unsupported content types, oversized API mutation bodies, invalid numeric ranges, unknown strategies, duplicate routing identifiers, over-cap routing candidate/strategy lists, oversized Decision Explorer output, and invalid load-shedding metadata with controlled error responses. Error bodies should not include stack traces, exception class names, secrets, or diagnostic internals.

Rejected requests must not construct or mutate `CloudManager`. Read-only evaluation requests must remain recommendation-only and keep `metricsPreview.emitted` set to `false`.

Request-size limits are enforced for `/api/**` POST, PUT, and PATCH requests. The default limit is 16 KiB and can be changed with `loadbalancerpro.api.max-request-bytes`. Optional proxy mode has a separate request-body ceiling, `loadbalancerpro.proxy.max-request-bytes`, defaulting to 64 KiB; declared oversize is rejected before reading, and unknown-length overflow aborts with HTTP 413 without retrying or penalizing an upstream. Proxy responses use a fixed streaming buffer and `loadbalancerpro.proxy.max-response-bytes=0` by default; a positive ceiling rejects known oversize before commitment or aborts an already-committed streamed response without appending an error body.

Reverse-proxy forwarding metadata fails closed by default: caller-supplied `Forwarded` and `X-Forwarded-*` values are stripped and replaced from the immediate connection. Append mode honors an inbound chain only when the immediate peer matches an explicitly configured IPv4 or IPv6 literal CIDR; hostnames are not resolved for trust decisions. Per-route static header rewrites are validated operator configuration applied after this policy, so access to proxy configuration or reload must remain an operator boundary.

Routing comparison and Decision Explorer requests also have an absolute 32-candidate and five-strategy ceiling.
`loadbalancerpro.api.max-candidates` and `loadbalancerpro.api.max-strategies` can lower those limits, and
`loadbalancerpro.api.max-decision-explorer-response-bytes` bounds the counting-serialization pass for Explorer output
(16 MiB by default, with a one-byte minimum and 64 MiB hard maximum). Candidate and strategy violations fail with
HTTP 400 before comparison/Explorer payload construction. The output guard stops serialization once the ceiling
would be crossed and returns structured HTTP 400; out-of-range settings fail application configuration validation.
This is a local process bound, not load/stress proof or a substitute for deployment-level quotas.

The bounded active-experiment operator contract is exposed under `/api/lab/experiments`: arm, gated start, explicit request batches, evaluate, cancel, current status, and terminal record retrieval. Mutation requests carry bounded identifiers and numeric controls but no target URL or address; runtime targets must come from an immutable repository-controlled catalog, must exactly match a catalog scenario, and must use literal HTTP loopback addresses. The production catalog is empty by default. Candidate installation additionally requires active-experiment mode, `active-experiment-enabled`, the separate default-off `gated-actuation-enabled` property, and authenticated API-key or OAuth2 allocation-role mode; explicit authentication-disabled mode cannot actuate. Start accepts only `install-candidate-allocation` and binds it to the stored server-side decision ID, `ARMED` state, and exact current record fingerprint. Client explanations, factors, targets, URLs, headers, credentials, routing keys, affinity values, commands, filenames, processes, and opaque payloads cannot authorize it. Only one experiment may be active; unknown, expired, stale, conflicting, malformed, disabled, unsupported, and terminal commands fail closed. Synchronized request-ID caching prevents a concurrent identical replay from causing a second allocation revision. Shutdown/cancel/evaluation restores the recorded baseline, and the existing allocation seam does not report success unless its atomic apply/read-back/rollback contract succeeds. Records and actuation receipts are bounded privacy-safe snapshots with fingerprinted operator-action chains and no target address exposure. With an explicit existing absolute local journal directory, the same accepted lifecycle is projected to force-synchronized append-only evidence and reconciled before new experiment admission; blank configuration remains process-local only.

Durable evidence endpoints beneath `/api/lab/experiments/durable` expose only bounded discovery summaries, verification findings, restart status, reconstructed export, terminal manifests, opaque quarantine metadata, and retention/compaction actions. They accept bounded experiment IDs or retention values, never paths, raw journal bytes, arbitrary filenames, deletion requests, or unresolved-evidence mutation. Compaction requires exact verification and terminal replay; active or corrupt evidence is preserved. See [`architecture/ENTERPRISE_LAB_DURABLE_EVIDENCE.md`](architecture/ENTERPRISE_LAB_DURABLE_EVIDENCE.md) for the append, recovery, retention, proof, and not-proven boundaries.

The test/tool-only `--enterprise-lab-experiment-proof=completion|rollback|all` command is a separate foreground proof path and does not start the API server. It creates exactly three ephemeral literal-`127.0.0.1` backends, supplies their addresses directly to the existing repository-controlled target catalog, composes the same observation, decision, allocation, lifecycle, evaluator, and operator services, and accepts no backend URL, host, port, scenario, cloud, tenant, or credential input. Completion and rollback evidence is written only beneath ignored `target/` paths as fingerprinted JSON, a Markdown summary, and metadata; `scripts/smoke/enterprise-lab-experiment-proof.ps1` compiles and invokes the test-scope `EnterpriseLabProofToolsApplication` and verifies baseline restoration. The production Spring Boot application does not dispatch proof flags and the server jar contains no proof runner, report, exporter, command, or helper classes. The proof is synchronous and bounded by the existing request, batch, duration, expiration, timeout, action-history, and experiment-history ceilings. Its real loopback outcomes and deterministic policy/lifecycle checks do not establish durable audit storage, multi-instance coordination, restart replay, production traffic control, load or stress performance, SLOs, live cloud or tenant behavior, deployment certification, or production readiness.

The durable-recovery, evidence-ownership, allocation, and independent-supervisor proofs use the same test-scope launcher through their matching scripts under `scripts/smoke/`. The durable-recovery proof uses target-only local data plus three literal-loopback ephemeral backends to prove live append, a closed-writer interruption boundary, repeated startup reconciliation, normal terminal preservation, middle-corruption and partial-tail quarantine, unresolved-evidence retention, active-compaction rejection, and verified terminal compaction. These proof tools do not claim an operating-system crash, power-loss durability, distributed ownership, signer identity, production traffic, or deployment readiness.

Optional reverse proxy mode at `/proxy/**` is disabled by default and forwards caller traffic only when `loadbalancerpro.proxy.enabled=true` and upstreams are configured. It uses existing request-level routing strategy concepts, skips upstreams configured as unhealthy, copies only practical safe headers, and returns selected-upstream evidence headers. Optional active health checks are disabled by default, use dedicated daemon workers to probe configured upstream URLs only, apply bounded consecutive rise/fall thresholds, and never override `healthy=false`; forwarding and status threads only read process-local health snapshots. Optional bounded retries, cooldown, and slow start are also disabled by default; retries default to `GET`/`HEAD`, non-idempotent retries require explicit opt-in, retry percentage credits cannot exceed one stored retry, full-jitter backoff is capped at 60 seconds, and recovery state is memory-only. `GET /api/proxy/status` exposes read-only proxy state, effective health/weight, retry-budget/backoff and cooldown/slow-start config, process-local counters, and report-only private-network live gate visibility; it does not trigger probe I/O, persist metrics, or provide reset/admin mutation controls. `GET /api/proxy/decisions/recent` exposes only the newest 100 actual upstream-attempt records plus bounded capture/drop counters; it omits request paths, queries, bodies, headers, cookies, routing keys, upstream URLs, and credentials, and it adds no reset or persistence surface. `POST /api/proxy/private-network-live-validation` is a command contract only: it validates request shape and offline gate status, returns `trafficExecuted=false`, does not call the live executor, does not write evidence or audit files, and does not send private-LAN or public traffic. Its planned evidence/audit fields point only to ignored `target/proxy-evidence/` outputs and require redaction before any future wiring. The static `/proxy-status.html` page reads the status endpoint only, keeps optional live-refresh state in memory only, and adds no backend write, reset, storage, cloud, or admin controls. The strategy demo lab, Java `ProxyDemoFixtureLauncher`, Maven exec launcher recipe, release-free distribution smoke scripts, local artifact verification scripts, CI `packaged-artifact-smoke` workflow artifact, `scripts/proxy-demo.ps1`, `scripts/proxy-demo.sh`, and the `proxy-demo-*` profiles use loopback fixture backends, explicit `auth.mode=none`, and printed curl recipes only; they do not add write endpoints, secrets, external URLs, Python/Node/Docker requirements for the Java path, release publication commands, release/tag commands, or public network dependencies. Real-backend examples under `docs/examples/proxy` are copy/adapt local placeholders only, keep upstream URLs loopback/private, and also require an explicit auth-mode choice. Proxy mode does not construct `CloudManager`, mutate cloud state, write reports, or add external services. In API-key mode, `/proxy/**`, `GET /api/proxy/status`, `GET /api/proxy/decisions/recent`, and the command contract require `X-API-Key` regardless of profile. In OAuth2 mode, those proxy surfaces require the configured allocation role, which defaults to `operator`. Explicit none-mode demos are open by design and emit a warning, so bind them to loopback or a trusted private network unless deployment-specific auth, TLS, ingress, and rate limits are in place. Optional inbound HTTPS/SNI/reload and verified backend trust/mTLS use named Spring SSL bundles as documented in `DEPLOYMENT.md`; hostname verification cannot be disabled. Optional WebSocket passthrough is separately disabled by default, applies bounded message/send/idle limits, reuses proxy routing and concurrency controls, and remains subject to the same inbound authentication; route header policy must remove proxy credentials that an upstream must not receive. Treat it as a lightweight forwarding aid, not a production gateway, benchmark proof, certification, legal compliance proof, identity proof, WAF, or certificate authority.

Process-local consistent hashing can use the immediate peer address or a configured request header. Header-derived hash keys are trusted routing metadata only when a trusted ingress strips and sets them; sensitive, forwarding, and hop-by-hop headers are rejected, key values are not logged or returned, and `client-ip` does not accept caller-supplied forwarding metadata. Optional route cookie affinity is disabled by default and requires an operator-supplied HMAC key from a secret source. Its route-bound `HttpOnly`, `SameSite=Lax` cookie is only a backend-routing hint: it is not authentication, authorization, a server session, CSRF protection, or tenant isolation, and unhealthy, drained, or otherwise unavailable pins fall back to the configured strategy. `GET /api/proxy/status` reports the hash-source label and affinity enablement, but never the HMAC key, cookie name, or cookie value. Ring and cookie-routing behavior remain per-process and do not establish multi-instance affinity, distributed session state, benchmark evidence, or production certification.

## Out Of Scope

The repository does not currently provide WAF rules, distributed quotas, bot detection, credential rotation, customer identity lifecycle management, TLS certificates, or production incident-response automation. Those controls belong in the deployment platform and should be reviewed separately before public exposure.
